**Settings → GitLab** でセルフホストの GitLab インスタンスを一度だけ接続します。接続後は、ソースブランチ名・タイトル・説明にイシュー識別子（例 `MUL-123`）を含む merge request が、その[イシュー](/issues)に**自動でリンク**され、イシューサイドバーの **Merge requests** に表示されます — そして MR がマージされると、イシューが **Done** に移動します。

接続は **workspace ごとに分離**されています。各 workspace は自分の GitLab base URL を指し、自分の webhook シークレットトークンを保持し、（任意で）自分の personal access token を持ちます。イシュー単位のセットアップは不要で、すべて識別子で駆動されます。

## 連携でできること

| 画面 | 挙動 |
|---|---|
| **Settings → GitLab** | workspace の管理者・オーナーには GitLab タブが表示されます：マスタートグル、**Connection** カード（base URL + 任意の PAT）、**Webhook** カード（URL + シークレットトークン）、機能スイッチ（MR サイドバー、Co-authored-by、自動リンク）。 |
| **イシューサイドバー → Merge requests** | このイシューに自動リンクされた各 MR を、タイトル・プロジェクトパス・状態（`Open` / `Merged` / `Closed`）・作者付きで表示。行をクリックすると GitLab の MR に移動します。 |
| **Webhook（バックグラウンド）** | Merge Request Hook の配信ごとに、Multica は MR 行を upsert し、MR 内のイシュー識別子を走査し、リンク行を（再）構築します。冪等で、同じ配信のリプレイは no-op です。 |
| **マージ時の自動ステータス変更** | MR が `merged` に遷移すると、`Done` でも `Cancelled` でもないリンク済みイシューはすべて `Done` に移動します。ステータス変更はタイムラインに記録されます。 |

ミラーされるのは MR 本体のみです。コミット、MR のないブランチ参照、CI パイプライン状態は**モデル化されません**。連携は意図的に狭く保たれています。

## 識別子のマッチング方法

webhook は次の 3 フィールドからこの順で識別子を抽出します：**MR ソースブランチ**、**MR タイトル**、**MR 説明**。マッチャーは：

- 大文字小文字を区別しません — `mul-123`、`MUL-123`、`Mul-123` すべてマッチします。
- 境界付き — 左側の `\b` と右側の数字アンカーにより、`v1.2-3` のようなバージョン番号やメール風の文字列を拾いません。
- workspace スコープ — その workspace 自身の[イシュー接頭辞](/workspaces)のみマッチします。接頭辞が `MUL` の workspace では、整数が別のイシューに一致しても `FOO-1` は無視されます。
- 重複排除 — 説明に `MUL-1, MUL-1` と書いてもイシューは 1 回だけリンクされます。

1 つの MR で**複数のイシュー**を参照できます。`Closes MUL-1, MUL-2` は MR を両方にリンクし、マージすると両方を `Done` に進めます。

## マージ → Done の自動ルール

MR の状態が `merged` に切り替わると、リンク済みの各イシューが評価されます：

| イシューの現在のステータス | 結果 |
|---|---|
| `done` | 変更なし（すでに終端）。 |
| `cancelled` | **変更なし** — cancelled はユーザーが明示的に作業を中止したことを意味し、連携はそのシグナルを上書きしません。 |
| その他すべて（`todo`、`in_progress`、`in_review`、`blocked`、`backlog`） | `done` に移動。 |

MR を**マージせずに**クローズした場合は、MR カードの状態を `Closed` に更新するだけです。リンク済みイシューはそのままで — マージなしクローズが何を意味するかはユーザーが決めます。

<Callout type="info">
イシューの購読者は、人がイシューを移動したときと同じように、ステータス変更の inbox 通知を受け取ります。
</Callout>

## 自動リンクされないもの

- **コミットメッセージ内の識別子** — 走査されるのはソースブランチ / タイトル / 説明のみです。`MUL-123: fix login` というコミットは、同じ文字列が MR タイトルか説明にも現れない限り自動リンクされません。
- **MR コメント内の識別子** — 走査されるのは MR 自身のメタデータのみで、後続の GitLab note は無視されます。
- **webhook のないプロジェクトの MR** — Multica を指す Merge request events webhook がなければ、サーバーは配信を受け取りません。
- **MR をイシューに手動リンク** — まだ UI はありません。チームの慣習が Multica の読まない場所に識別子を置いているなら、MR タイトルか説明に追加してください。

## セルフホストのセットアップ

GitLab は **workspace ごと**に UI から設定します — GitHub App のようなグローバルインストールはありません。運用者レベルの手順は任意の暗号化キー（後述）だけで、それ以外はすべて workspace 管理者が **Settings → GitLab** で行います。

### 1. UI から接続

1. オーナーまたは管理者として **Settings → GitLab** を開きます。
2. **Connection** カードに GitLab の **base URL**（例 `https://gitlab.example.com`、HTTP または HTTPS）を入力し、**Connect** をクリックします。
3. 任意で **personal access token**（`glpat-…`）を貼り付けます。API enrichment のみに使われ、**暗号化して保存**されます — 再表示はされません。enrichment が不要なら空のままにします。

### 2. GitLab に webhook を追加

Multica の **Webhook** カードを開くと、**Webhook URL** と**シークレットトークン**が表示されます。次に GitLab プロジェクトで：

| GitLab のフィールド（**Settings → Webhooks**） | 値 |
|---|---|
| **URL** | Multica の **Webhook URL** — `https://<api-host>/api/webhooks/gitlab`。 |
| **Secret token** | Multica の Webhook カードの**シークレットトークン**（管理者/オーナーにのみ表示）。Multica は `X-Gitlab-Token` ヘッダーで送り返し、一致しない配信は拒否します。 |
| **Trigger** | **Merge request events**（object kind は `Merge Request Hook`）にチェックします。 |

GitLab で webhook を保存し、**Test → Merge request events**（または実際の MR を開く）で配信を確認します。

<Callout type="warning">
配信を認証するのは**シークレットトークン**だけです — Multica は受信した `X-Gitlab-Token` ヘッダーを保存済みトークンと照合します。Webhook カードの **Regenerate** でローテーションできます。ローテーション後は新しい値を GitLab に貼り直すのを忘れずに。そうしないと配信が拒否され始めます。
</Callout>

### 3. 任意 — personal access token を暗号化保存

接続に PAT を保存する場合は、運用者レベルの環境変数を 1 つ設定して保存時に暗号化します：

```dotenv
# 任意。GitLab personal access token を保存時に暗号化するための
# base64 エンコードされた 32 バイトのキー。生成: openssl rand -base64 32
MULTICA_GITLAB_SECRET_KEY=
```

このキーは PAT の保存にのみ影響します。webhook フロー（URL + シークレットトークン + Merge request events）には不要です — PAT を保存しないなら空のままにします。

### 4. 検証

ソースブランチ / タイトル / 説明にイシュー識別子を含む MR を開くと — 数秒でそのイシューの詳細ページに **Merge requests** ブロックが現れます。MR をマージすると、リンク済みイシューが **Done** に移動します。

## 切断

**Settings → GitLab** で、管理者とオーナーは **Disconnect** できます。Multica はその GitLab インスタンスからの webhook の受信を停止します。既存の merge request ミラーとリンクは保持されるため、過去のイシューサイドバーは当時リンクされていたものを表示し続けます。いつでも再接続して更新を再開できます。GitLab プロジェクト側から webhook を削除することもできます。

## 権限と可視性

- **接続 / 切断 / トークンの再生成**には workspace の**オーナーまたは管理者**が必要です。webhook シークレットトークンは管理者とオーナーにのみ表示されます。
- イシューの **Merge requests** サイドバーは、そのイシューを読める人なら誰でも見えます — イシュー詳細の他の部分と同じ権限です。
- 任意の PAT は API enrichment に**読み取り専用**で使われます。Multica がコミット・note・パイプライン状態を GitLab に書き戻すことはありません。

## 制限

現時点で気をつけるべき点：

- **手動リンク UI はまだありません** — MR をリンクする唯一の方法は、識別子をソースブランチ・タイトル・説明に入れることです。
- **CI / パイプライン状態なし** — ミラーされるのは MR 本体のみです。パイプライン状態、review note、reviewer は Multica に表示されません。
- **マージ → Done ルールの workspace レベル設定なし** — 固定のデフォルト（`merged → done`、ただし `cancelled` は除く）です。
