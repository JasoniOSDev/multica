在 **Settings → GitLab** 里一次性连接你的自建 GitLab 实例。连接后，凡是源分支名、标题或描述里包含 issue 编号（比如 `MUL-123`）的 merge request 都会**自动关联**到对应 [issue](/issues)，出现在 issue 侧边栏的 **Merge requests** 区块里 —— 当该 MR 被 merge 时，issue 自动转 **Done**。

连接是**按 workspace 隔离**的：每个 workspace 指向自己的 GitLab base URL，持有自己的 webhook 密钥令牌，以及（可选的）自己的 personal access token。无需逐个 issue 配置 —— 整个流程都由编号驱动。

## 集成做了什么

| 界面 | 行为 |
|---|---|
| **Settings → GitLab** | workspace 管理员和所有者能看到 GitLab tab：总开关、**Connection** 卡片（base URL + 可选 PAT）、**Webhook** 卡片（URL + 密钥令牌）、以及功能开关（MR 侧边栏、Co-authored-by、自动关联）。 |
| **Issue 侧边栏 → Merge requests** | 自动关联到该 issue 的每个 MR，含标题、项目路径、状态（`Open` / `Merged` / `Closed`）和作者。点击一行跳转到 GitLab 上的 MR。 |
| **Webhook（后台）** | 每次 Merge Request Hook 投递时，Multica upsert MR 行、扫描 MR 里的 issue 编号、并（重新）建立关联行。幂等 —— 重放一次投递是 no-op。 |
| **Merge 时自动改状态** | 当 MR 转为 `merged`，每个尚未 `Done` 或 `Cancelled` 的关联 issue 都被转为 `Done`，状态变更会记入时间线。 |

只镜像 MR 本身。提交、没有开启 MR 的分支引用、以及 CI 流水线状态都**不**建模。集成有意做得很窄。

## 编号如何匹配

webhook 按顺序从三个字段提取编号：**MR 源分支**、**MR 标题**、**MR 描述**。匹配规则：

- 大小写不敏感 —— `mul-123`、`MUL-123`、`Mul-123` 都能匹配。
- 有边界 —— 左侧 `\b`、右侧数字锚点，避免抓到 `v1.2-3` 这类版本号或邮箱样式字符串。
- 按 workspace 限定 —— 只匹配该 workspace 自己的 [issue 前缀](/workspaces)。前缀为 `MUL` 的 workspace 里，`FOO-1` 会被忽略，即使整数能对上另一个 issue。
- 去重 —— 描述里写 `MUL-1, MUL-1` 只关联一次。

一个 MR 里可以引用**多个 issue**。`Closes MUL-1, MUL-2` 会把 MR 关联到两者，merge 后两者都推进到 `Done`。

## merge 自动转 Done 规则

当 MR 状态翻转为 `merged`，每个关联 issue 都会被判定：

| issue 当前状态 | 结果 |
|---|---|
| `done` | 不变（已是终态）。 |
| `cancelled` | **不变** —— cancelled 表示用户明确放弃了这项工作，集成不会覆盖这个信号。 |
| 其他任何状态（`todo`、`in_progress`、`in_review`、`blocked`、`backlog`） | 转为 `done`。 |

**不 merge** 只关闭 MR，只会把 MR 卡片状态更新为 `Closed`，关联 issue 维持原状 —— 关闭不合并意味着什么由用户决定。

<Callout type="info">
issue 的订阅者会收到状态变更的 inbox 通知，和人工移动 issue 时的体验一致。
</Callout>

## 哪些不会自动关联

- **提交信息里的编号** —— 只扫描源分支 / 标题 / 描述。标题为 `MUL-123: fix login` 的提交不会自动关联，除非同样的字符串也出现在 MR 标题或描述里。
- **MR 评论里的编号** —— 只扫描 MR 自身的元数据，后续 GitLab note 会被忽略。
- **没配 webhook 的项目里的 MR** —— 没有指向 Multica 的 Merge request events webhook，服务端根本收不到投递。
- **手动把 MR 关联到 issue** —— 暂时没有这个 UI。如果你们的约定把编号放在 Multica 没读的地方，请把它加到 MR 标题或描述里。

## 自托管配置

GitLab 是**按 workspace** 在 UI 里配置的 —— 没有 GitHub App 那种全局安装。唯一的运维层步骤是一个可选的加密密钥（见下文）；其余都由 workspace 管理员在 **Settings → GitLab** 里完成。

### 1. 在 UI 里连接

1. 以所有者或管理员身份打开 **Settings → GitLab**。
2. 在 **Connection** 卡片里填入 GitLab **base URL**（比如 `https://gitlab.example.com`，HTTP 或 HTTPS），点 **Connect**。
3. 可选地粘贴一个 **personal access token**（`glpat-…`）。它只用于 API enrichment，**加密存储** —— 不再回显。不需要 enrichment 就留空。

### 2. 在 GitLab 里添加 webhook

打开 Multica 的 **Webhook** 卡片 —— 它会显示 **Webhook URL** 和 **密钥令牌**。然后在你的 GitLab 项目里：

| GitLab 字段（**Settings → Webhooks**） | 值 |
|---|---|
| **URL** | Multica 里的 **Webhook URL** —— `https://<api-host>/api/webhooks/gitlab`。 |
| **Secret token** | Multica Webhook 卡片里的**密钥令牌**（只对管理员/所有者显示）。Multica 会以 `X-Gitlab-Token` 头回传它，不匹配的投递会被拒绝。 |
| **Trigger** | 勾选 **Merge request events**（object kind 为 `Merge Request Hook`）。 |

在 GitLab 里保存 webhook，然后用 **Test → Merge request events**（或开一个真实 MR）确认投递成功。

<Callout type="warning">
**密钥令牌**是唯一用来鉴别投递的东西 —— Multica 拿进来的 `X-Gitlab-Token` 头与存储的令牌比对。用 Webhook 卡片里的 **Regenerate** 轮换它；轮换后记得把新值粘回 GitLab，否则投递会开始被拒。
</Callout>

### 3. 可选 —— 加密 personal access token

如果你在连接上存了 PAT，设置一个运维层环境变量让它加密存储：

```dotenv
# 可选。base64 编码的 32 字节密钥，用于加密 GitLab personal access
# token 的静态存储。生成方式：openssl rand -base64 32
MULTICA_GITLAB_SECRET_KEY=
```

这个密钥只影响 PAT 存储。webhook 流程（URL + 密钥令牌 + Merge request events）不依赖它 —— 不存 PAT 就留空。

### 4. 验证

打开任意一个源分支 / 标题 / 描述里含 issue 编号的 MR —— 几秒内该 issue 详情页就会出现 **Merge requests** 区块。merge 这个 MR，关联 issue 转 **Done**。

## 断开连接

在 **Settings → GitLab**，管理员和所有者可以 **Disconnect**。Multica 停止接收来自该 GitLab 实例的 webhook。已有的 merge request 镜像与关联会保留，历史 issue 侧边栏仍能看到当时关联了什么；随时可以重新连接以恢复更新。你也可以从 GitLab 项目侧移除 webhook。

## 权限与可见性

- **连接 / 断开 / 轮换令牌**需要 workspace **所有者或管理员**。webhook 密钥令牌只对管理员和所有者显示。
- issue 上的 **Merge requests** 侧边栏对任何能读该 issue 的人可见 —— 权限与 issue 详情其余部分一致。
- 可选 PAT 仅用于**只读**的 API enrichment。Multica 永远不会把提交、note 或流水线状态推回 GitLab。

## 局限

目前几个需要注意的地方：

- **暂无手动关联 UI** —— 关联 MR 的唯一方式是让编号出现在源分支、标题或描述里。
- **无 CI / 流水线状态** —— 只镜像 MR 本身。流水线状态、review note 和 reviewer 不在 Multica 里呈现。
- **merge → Done 规则没有 workspace 级配置** —— 它是固定默认（`merged → done`，除非 `cancelled`）。
