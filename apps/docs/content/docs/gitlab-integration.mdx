Connect your self-hosted GitLab instance once in **Settings → GitLab**. After that, any merge request whose source branch, title, or description contains an issue identifier (for example `MUL-123`) is **auto-linked** to that [issue](/issues), appears under **Merge requests** in the issue sidebar, and — when the MR is merged — moves the issue to **Done**.

The connection is **workspace-scoped**: each workspace points at its own GitLab base URL, holds its own webhook secret token, and (optionally) its own personal access token. There is no per-issue setup — the whole flow is identifier-driven.

## What the integration does

| Surface | Behavior |
|---|---|
| **Settings → GitLab** | Workspace admins and owners see the GitLab tab with a master toggle, the **Connection** card (base URL + optional PAT), the **Webhook** card (URL + secret token), and feature switches (MR sidebar, Co-authored-by, auto-link). |
| **Issue sidebar → Merge requests** | Every MR auto-linked to this issue, with title, project path, state (`Open` / `Merged` / `Closed`), and author. Click a row to jump to the MR on GitLab. |
| **Webhook (background)** | On every Merge Request Hook delivery, Multica upserts the MR row, scans the MR for issue identifiers, and (re)builds the link rows. Idempotent — replaying a delivery is a no-op. |
| **Auto-status on merge** | When an MR transitions to `merged`, every linked issue not already `Done` or `Cancelled` is moved to `Done`. The status change is timeline-logged. |

Only the MR itself is mirrored. Commits, branch refs without an open MR, and CI pipeline states are **not** modeled. The integration is intentionally narrow.

## How identifiers are matched

The webhook extracts identifiers from three fields, in this order: **MR source branch**, **MR title**, **MR description**. The matcher is:

- Case-insensitive — `mul-123`, `MUL-123`, `Mul-123` all match.
- Bounded — a `\b` on the left and a digit anchor on the right keep it from grabbing version numbers like `v1.2-3` or email-style strings.
- Workspace-scoped — only matches the workspace's own [issue prefix](/workspaces). `FOO-1` in a workspace whose prefix is `MUL` is ignored, even if the integer matches another issue.
- Deduplicated — listing `MUL-1, MUL-1` in the description links the issue once.

You can reference **multiple issues** in one MR. `Closes MUL-1, MUL-2` links the MR to both, and merging it advances both to `Done`.

## The auto-merge-to-Done rule

When an MR's state flips to `merged`, every linked issue is evaluated:

| Issue current status | Result |
|---|---|
| `done` | No change (already terminal). |
| `cancelled` | **No change** — cancelled means the user explicitly abandoned the work; the integration does not override that signal. |
| Anything else (`todo`, `in_progress`, `in_review`, `blocked`, `backlog`) | Moved to `done`. |

Closing an MR **without** merging it only updates the MR card's state to `Closed`. The linked issues stay where they were — the user is the one who decides what closing-without-merge means.

<Callout type="info">
Subscribers of the issue receive an inbox notification for the status change, the same way they would if a human had moved it.
</Callout>

## What's not auto-linked

- **Identifiers in commit messages** — only source branch / title / description are scanned. A commit titled `MUL-123: fix login` does not auto-link unless the same string also appears in the MR title or description.
- **Identifiers in MR comments** — only the MR's own metadata is scanned; later GitLab notes are ignored.
- **MRs in projects without the webhook** — without a Merge request events webhook pointing at Multica, the server never receives the delivery.
- **Manually linking an MR to an issue** — there is no UI for this yet. If your team's convention puts identifiers in a place Multica isn't reading, add them to the MR title or description.

## Self-host setup

GitLab is configured **per workspace** from the UI — there is no global GitHub-App-style install. The only operator-level step is an optional encryption key (below); everything else is done by a workspace admin in **Settings → GitLab**.

### 1. Connect from the UI

1. Open **Settings → GitLab** as an owner or admin.
2. In the **Connection** card, enter your GitLab **base URL** (e.g. `https://gitlab.example.com`, HTTP or HTTPS) and click **Connect**.
3. Optionally paste a **personal access token** (`glpat-…`). It is used only for API enrichment and is stored **encrypted** — never shown again. Leave it empty if you don't need enrichment.

### 2. Add the webhook in GitLab

Open the **Webhook** card in Multica — it shows a **Webhook URL** and a **Secret token**. Then in your GitLab project:

| GitLab field (**Settings → Webhooks**) | Value |
|---|---|
| **URL** | The **Webhook URL** from Multica — `https://<api-host>/api/webhooks/gitlab`. |
| **Secret token** | The **Secret token** from Multica's Webhook card (only shown to admins/owners). Multica sends it back as the `X-Gitlab-Token` header and rejects deliveries that don't match. |
| **Trigger** | Tick **Merge request events** (object kind `Merge Request Hook`). |

Save the webhook in GitLab, then use **Test → Merge request events** (or open a real MR) to confirm delivery.

<Callout type="warning">
The **Secret token** is the only thing that authenticates a delivery — Multica compares the incoming `X-Gitlab-Token` header against the stored token. Use **Regenerate** in the Webhook card to rotate it; remember to paste the new value back into GitLab afterwards, or deliveries start getting rejected.
</Callout>

### 3. Optional — encrypt the personal access token at rest

If you store a PAT on the connection, set one operator-level environment variable so it is encrypted at rest:

```dotenv
# Optional. Base64-encoded 32-byte key used to encrypt the GitLab
# personal access token at rest. Generate with: openssl rand -base64 32
MULTICA_GITLAB_SECRET_KEY=
```

This key only affects PAT storage. The webhook flow (URL + secret token + Merge request events) works without it — leave it unset if you don't store a PAT.

### 4. Verify

Open any MR whose source branch / title / description contains an issue identifier — within a few seconds the **Merge requests** block appears on that issue's detail page. Merge the MR and the linked issue moves to **Done**.

## Disconnecting

In **Settings → GitLab**, admins and owners can **Disconnect**. Multica stops receiving webhooks from that GitLab instance. Existing merge request mirrors and links are kept, so historical issue sidebars still show what was linked; reconnect any time to resume updates. You can also remove the webhook from the GitLab project side.

## Permissions and visibility

- **Connect / disconnect / regenerate token** require workspace **owner or admin**. The webhook secret token is shown only to admins and owners.
- The **Merge requests** sidebar on an issue is visible to anyone who can read the issue — same permissions as the rest of issue detail.
- The optional PAT is used **read-only** for API enrichment. Multica never pushes commits, notes, or pipeline status back to GitLab.

## Limitations

A few rough edges to be aware of today:

- **No manual link UI yet** — the only way to link an MR is to have the identifier in its source branch, title, or description.
- **No CI / pipeline state** — only the MR itself is mirrored. Pipeline status, review notes, and reviewers are not surfaced in Multica.
- **No workspace-level config** for the merge → Done rule — it's a fixed default (`merged → done`, unless `cancelled`).
